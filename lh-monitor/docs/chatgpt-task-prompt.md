[LH 수원 공고 GitHub 알림 감시 — 최종 운영본]

매 실행마다 아래 GitHub Raw JSON만 확인한다.

https://raw.githubusercontent.com/lopy1023-prog/naver-exhibition-monitor/main/data/lh/lh-report.json

LH청약플러스 사이트를 별도로 검색하거나 재검증하지 않는다.
웹 검색 결과나 LH 페이지 직접 접근 성공·실패를 감시 상태 판정에 사용하지 않는다.
PDF/HWP/HWPX/XLS/XLSX 등 첨부파일도 확인하지 않는다.

감시 및 신규 알림 판단은 오직 `lh-report.json`의 값만 기준으로 한다.

외부 예약 서비스나 별도의 외부 감시 시스템을 추가하지 않는다.


[1. 실행 방식]

기존 LH 알림 실행 방식을 그대로 유지한다.

GitHub 수집기가 매시간 정확히 갱신될 필요는 없다.

실제 GitHub 자동 실행은 일정한 간격이 아니라 다소 불규칙하게 실행될 수 있으며,
하루 1~2회 정도 정상적으로 갱신되고 있다면 충분한 것으로 본다.

따라서 `syncedAt`이 2시간 이상 갱신되지 않았다는 이유만으로
`LH 감시 갱신 중단`, `감시 오류`, `갱신 지연` 등의 알림을 보내지 않는다.

`root.syncedAt`은 참고용으로만 사용할 수 있으며,
신규 공고 알림 여부를 결정하는 기준으로 사용하지 않는다.


[2. 감시 데이터]

신규 공고 및 변경사항 감시는 `alertHistory`를 기준으로 한다.

핵심 감시 값은:

- `alertHistory[].alertId`
- `alertHistory[].panId`
- `alertHistory[].title`
- `alertHistory[].detailUrl`
- `alertHistory[].kind`
- `alertHistory[].kinds`

등 `alertHistory`에 실제 존재하는 값이다.

없는 값을 추정하거나 만들어내지 않는다.

`alertHistory[].detectedAt`은 해당 alert가 감지된 시각을 나타내는 참고값일 뿐이다.

다음 용도로 사용하지 않는다.

- 신규/중복 여부 판단
- GitHub 갱신 정상 여부 판단
- `syncedAt` 대체
- 공고 소급 알림 판단

신규/중복 여부의 유일한 기준은 `alertId`다.


[3. 최초 기준선]

감시를 시작한 시점에 `alertHistory`에 이미 존재하는 모든 `alertId`는
기존 기준 데이터로 간주한다.

기존 `alertHistory`에 이미 있던 공고를 소급하여 알리지 않는다.

최초 기준선에 존재한 `alertId` 전체를 기존 확인 완료 데이터로 취급하고,
그 이후 새롭게 추가된 `alertId`만 감시 대상으로 한다.

즉:

- 최초 실행 전에 이미 존재한 `alertId` → 알림 금지
- 이후 새로 생성된 `alertId` → 신규 알림 후보

기존 데이터가 오래되었는지 최근 데이터인지와 관계없이
기준선에 이미 존재했다면 소급 알림하지 않는다.


[4. 신규 알림 판단]

`alertHistory`에서 이전 실행까지 확인한 적 없는
새로운 `alertId`만 알림 대상으로 판단한다.

중복 판단의 유일한 기준은 `alertId`다.

- 같은 `alertId` → 다시 알리지 않는다.
- 새로운 `alertId` → 새 알림 후보
- 같은 `panId` + 새로운 `alertId` → 변경 알림 후보
- 제목이 같아도 새로운 `alertId` → 새 알림 후보
- `detectedAt`이 달라도 `alertId`가 같으면 → 다시 알리지 않는다.

이미 한 번 알린 `alertId`는 이후 다시 등장하더라도 절대 다시 알리지 않는다.


[5. 지역 범위]

새로운 `alertId`가 발견되면 해당 공고가 아래 범위에 해당하는지 확인한다.

알림 대상:

1. 수원 직접 관련 공고
2. 수원이 포함될 가능성이 있는 경기남부 공고
3. 수원이 포함될 가능성이 있는 경기도 단위 공고
4. 수원이 포함될 가능성이 있는 수도권 단위 공고
5. 수원이 포함될 가능성이 있는 전국 단위 공고

즉, 제목이나 `alertHistory`의 기존 정보상 범위가 다음과 같은 경우 알림 후보로 본다.

- 수원
- 수원시
- 경기남부
- 경기
- 경기도
- 수도권
- 전국

수원이 직접 명시되지 않았더라도
경기남부·경기·경기도·수도권·전국 단위 모집이라면
수원이 포함될 가능성이 있으므로 알림 대상에 포함한다.

반대로 `alertHistory`의 정보만으로 명백하게 수원과 무관한 특정 타 지역 전용 공고라면 알리지 않는다.

예:

- 부산광역시 전용
- 대구광역시 전용
- 광주광역시 전용
- 제주특별자치도 전용
- 특정 타 지역만 대상으로 하는 공고

지역 판단을 위해 LH 사이트나 첨부파일을 추가로 열어 확인하지 않는다.

`lh-report.json` 안의 정보만 사용한다.


[6. 신규 / 변경 구분]

새로운 `alertId`가 알림 대상 범위에 해당하면
`신규` 또는 `변경`으로 구분한다.

판단 순서는 다음과 같다.

### 신규

새로운 `alertId`의 `panId`가
기존 기준선 및 이전 `alertHistory`에서 확인된 적 없는 새로운 공고라면:

→ `신규`


### 변경

동일한 `panId`가 기존에 존재했는데
새로운 `alertId`가 추가된 경우:

→ `변경`

또한 `kind` 또는 `kinds`에 다음과 같은 기존 공고 변경 성격이 명확하게 나타나는 경우도 `변경`으로 본다.

- 재공고
- 추가모집
- 잔여세대
- 잔여물량
- 미계약분 재공급
- 후순위 접수
- 공급주택 목록 변경
- 공급수량 변경
- 수원 물량 변경
- 접수일정 변경
- 상태 변경
- 정정공고
- 수정공고
- 기타 기존 공고의 변경으로 명확히 표시된 항목

판단이 애매한 경우 임의로 내용을 추측하지 않는다.

가장 우선하는 기준은:

- 기존에 없던 `panId` → 신규
- 기존에 있던 `panId` + 새로운 `alertId` → 변경


[7. 기존 공고의 새로운 변경]

기존 공고라도 GitHub 수집기가 새로운 `alertId`를 생성하면
새로운 이벤트로 간주한다.

특히 다음 변경은 새로운 `alertId`가 생성된 경우 알림 대상이다.

- 재공고
- 추가모집
- 잔여세대
- 잔여물량
- 미계약분 재공급
- 후순위 접수
- 공급주택 목록 변경
- 공급수량 변경
- 수원 물량 변경
- 접수일정 변경
- 상태 변경
- 정정·수정공고
- 기타 GitHub 모니터가 새로운 변경으로 판정한 항목

단, 반드시 새로운 `alertId`가 있어야 한다.

같은 `alertId`라면 내용이 다시 노출되어도 재알림하지 않는다.


[8. 알림 형식]

알림은 최대한 간단하게 작성한다.

🏠 LH 공고 알림

- 공고명: `{title}`
- 구분: `신규` 또는 `변경`
- 링크: `{detailUrl}`

여러 건이면 한 번의 알림 안에서 각각 구분하여 작성한다.

불필요한 설명은 추가하지 않는다.

다음 내용은 기본 알림에 넣지 않는다.

- syncedAt
- detectedAt
- sourceStatus
- panId
- alertId
- 장문의 공고 요약
- 자격조건 추정
- 첨부파일 내용
- GPT의 추가 해석

사용자가 별도로 요청한 경우에만 추가 설명한다.


[9. 조용히 종료]

다음 경우에는 아무 메시지도 보내지 않는다.

- 새로운 `alertId`가 없음
- 새로운 `alertId`가 있지만 이미 알린 `alertId`임
- 새로운 `alertId`가 있지만 알림 대상 지역 범위가 아님
- 기존 기준선에 이미 존재하던 공고뿐임
- 소급 알림 대상밖에 없음

이 경우:

- `새로운 내용 없음`
- `정상 작동 중`
- `감시 정상`
- `신규 공고 없음`
- `변경 없음`

등의 메시지도 보내지 않는다.

완전히 조용히 종료한다.


[10. GitHub 갱신 관련 원칙]

GitHub 수집기는 매시간 정확히 실행될 필요가 없다.

사용자는 하루 1~2회 정도의 갱신이면 충분한 것으로 본다.

따라서 다음 상황만으로 사용자에게 오류 알림을 보내지 않는다.

- 2시간 이상 `syncedAt` 갱신 없음
- 몇 시간 동안 GitHub 자동 실행 없음
- 정각 또는 예정 시각에 실행되지 않음
- GitHub Actions 예약 실행 지연
- 하루 중 일부 시간대에 수집이 없음

`root.syncedAt`이 오래되었다는 이유만으로
`⚠️ LH 감시 갱신 중단` 알림을 보내지 않는다.

GitHub 실행 주기의 불규칙성은 신규 `alertId` 감시와 별개로 취급한다.

핵심 목적은 매시간 상태 보고가 아니라
새로운 LH 공고 및 변경사항을 놓치지 않고 알려주는 것이다.


[11. 외부 확인 금지]

감시 과정에서는 다음을 하지 않는다.

- LH청약플러스 직접 검색
- LH 웹페이지 재검증
- 일반 웹 검색으로 공고 확인
- 검색엔진 결과로 공고 존재 여부 판단
- PDF 확인
- HWP 확인
- HWPX 확인
- XLS/XLSX 확인
- 첨부파일 다운로드 및 분석
- 외부 예약 서비스 추가
- 별도 외부 모니터링 서비스 추가

GitHub `lh-report.json`에 포함된 데이터만 사용한다.


[12. 최종 원칙]

- 감시 데이터는 GitHub `lh-report.json`만 사용

- 신규/중복 판단의 유일한 기준은 `alertId`
- 기존 기준선의 `alertId`는 소급 알림 금지
- 이미 알린 동일 `alertId`는 재알림 금지
- 같은 `panId`라도 새로운 `alertId`면 변경 알림 가능
- 새로운 `panId` + 새로운 `alertId`면 신규로 판단
- 수원 직접 관련 공고 알림
- 경기남부 단위 공고 알림
- 경기·경기도 단위 공고 알림
- 수도권 단위 공고 알림
- 전국 단위 공고 알림
- 명백한 타 지역 전용 공고는 제외

- LH 사이트 재검색 금지
- 첨부파일 확인 금지

- GitHub가 매시간 정확히 갱신되지 않아도 오류 알림하지 않음

[확장 운영 규칙 — 2026-10-15, 충돌 시 이 규칙 우선]
이 작업은 기존 LH 수원 공고 알림의 연속이다. 이미 확인·알림한 alertId와 최초 기준선을 그대로 유지하며 초기화하거나 전체를 새 기준선으로 다시 삼지 않는다.

수원 관련 가능성이 있는 모든 공고와 안내를 알린다. 청년, 일반, 매입임대, 전세임대, 든든전세, 국민임대, 행복주택, 통합공공임대, 영구임대, 분양, 토지, 상가 및 기타 유형을 나이·소득·자산·방 개수·면적으로 사전 제외하지 않는다. 공고문, 공식 청약캘린더, 공지사항, 입주안내, 자료실, 입주계획, 공급계획, 선착순 계약 등 출처와 무관하게 report.alertHistory의 새 alertId를 확인한다. 수원 직접 공고와 경기남부·경기도·수도권·전국 범위 후보는 모두 포함한다. confirmedRegions에 화성/오산이 명시된 추가 지역 공고도 기존 요청대로 유지한다. 광역 후보는 수원 공급 확정으로 단정하지 않는다.

신규 공고, 정정·수정·추가·잔여 모집, 첨부 목록 변경, 접수 일정 변경, 선착순 재고의 목록 이탈/재등장을 모두 처리한다. kinds에 receptionStarted가 있거나 kind가 receptionStart이면 이미 알린 같은 panId라도 새 alertId에 대해 접수 시작 알림을 보낸다. officialStatus는 '접수 시작', officialStartTime은 '공식 접수 시작 시각 도래', officialStartDate는 '공식 접수 시작일 도래·시간 확인 필요'로 표시한다. GitHub가 같은 접수 시작의 상태·날짜·시간 경로를 합쳐 하나의 alertId 이벤트로 처리하므로 ChatGPT가 임의로 추가 이벤트를 만들지 않는다.

알림 형식은 공고명 / 구분(신규·변경·접수 시작 또는 시작일 도래) / 공식 링크로 간단히 유지한다. 접수 시작 알림에는 JSON에 있는 공식 시작일·시각만 추가하고 '대상 순위·자격별 접수 일정 확인 필요'를 표시한다. informationOnly=true인 공급계획·입주계획은 '계획/안내'라고 표시하고 지금 신청 가능하다고 말하지 않는다. inventoryUnavailable은 '선착순 목록에서 사라짐', inventoryAvailable은 '선착순 목록 재등장'으로 표시하며 소진·계약 완료를 추정하지 않는다.

sourceStatus=error이거나 JSON 조회 실패면 상태·기준선·확인한 alertId를 보존하고 임의의 신규 공고나 신규 없음으로 판단하지 않는다. syncedAt 지연만으로 경고하지 않는다. 새 알림 대상이 없으면 완전히 조용히 종료한다. LH 사이트 재검색·첨부 본문 확인·별도 예약 생성은 하지 않는다. 기존 실행 주기는 유지한다.
